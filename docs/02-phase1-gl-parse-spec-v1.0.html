01Монголын банкуудын хуулгын форматын каталог

Гол зарчим: банк бүрийн форматыг кодоор бичихгүй, өгөгдлөөр тодорхойлно. Шинэ банк, шинэ хувилбар нэмэгдэхэд програмист хэрэггүй — Format Registry-д нэг descriptor нэмнэ.

Доорх хүснэгт нь таван том банкны интернэт/корпорэйт банкнаас гардаг хуулгын түгээмэл шинжүүд. Бодит descriptor-уудыг Үе 1-ийн эхний 2 долоо хоногт банк бүрээс жинхэнэ хуулга цуглуулж баталгаажуулна (§7-гийн туршилтын багц).

Хуулга parse-ийн аюул нь унших боломжгүй файл биш (энэ нь харагддаг алдаа), харин буруу уншсан ч зөв юм шиг харагдах явдал: багана мөрөөсөө шилжих, огноо сар/өдөр солигдох, мянгатын таслал андуурагдах. Иймд ямар ч задлалтын үр дүн §4.4-ийн validation gate-ийг давахгүйгээр систем рүү нэвтэрч чадахгүй байх нь энэ баримтын хатуу шаардлага.

02Format Registry — форматыг өгөгдлөөр тодорхойлох

Банк бүрийн формат нэг descriptor (YAML) байна. Descriptor нь fingerprint (таних), extraction (задлах), validation (шалгах) гурван хэсэгтэй:

# format_registry/khan_ib_xlsx_v2026_1.yaml
id: khan.internet_bank.xlsx.v2026-1
bank: khan
channel: internet_bank          # internet_bank | corporate | branch_print
file_type: xlsx
account_kind: current_mnt       # Үе 1: зөвхөн MNT харилцах
status: active

fingerprint:                    # Шат 1-д таних дүрэм — оноо цуглуулах зарчмаар
  filename_pattern: ".*statement.*|.*huulga.*"     # +1 оноо
  sheet_keywords: ["Дансны хуулга", "Хуулгын хугацаа"] # +3 оноо
  column_signature:             # +5 оноо (хамгийн хүчтэй дохио)
    - "Гүйлгээний огноо"
    - "Дебит гүйлгээ"
    - "Кредит гүйлгээ"
    - "Үлдэгдэл"
  min_score: 6                  # энэ оноонд хүрвэл descriptor сонгогдоно

metadata_block:                 # хүснэгтийн дээрх мета мэдээлэл
  account_no:      { anchor: "Дансны дугаар", direction: right }
  account_name:    { anchor: "Хаяг, нэр",     direction: right }
  period:          { anchor: "Хуулгын хугацаа", direction: right, format: "range" }
  opening_balance: { anchor: "Эхний үлдэгдэл", direction: right, type: amount }
  closing_balance: { anchor: "Эцсийн үлдэгдэл", direction: right, type: amount }

table:
  header_row_match: ["Гүйлгээний огноо", "Үлдэгдэл"]  # энэ 2 үг нэг мөрөнд байвал толгой
  stop_row_match: ["Нийт дүн", "Гүйлгээний тоо"]      # хүснэгтийн төгсгөл
  columns:
    posted_at:       { aliases: ["Гүйлгээний огноо", "Огноо"], format: "%Y.%m.%d %H:%M|%Y.%m.%d" }
    branch:          { aliases: ["Салбар"], optional: true }
    debit:           { aliases: ["Дебит гүйлгээ", "Зарлага", "Debit"], type: amount }
    credit:          { aliases: ["Кредит гүйлгээ", "Орлого", "Credit"], type: amount }
    balance_after:   { aliases: ["Үлдэгдэл", "Эцсийн үлдэгдэл"], type: amount }
    counterparty_account: { aliases: ["Харьцсан данс"], optional: true }
    description:     { aliases: ["Гүйлгээний утга", "Утга"] }
  amount_locale: { thousands: ",", decimal: ".", negative: "minus|paren" }
  direction_mode: separate      # separate | signed
  continuation_rule: date_empty_merge_up   # PDF-д: огноогүй мөр = өмнөхийн үргэлжлэл

validation:
  balance_chain: required       # мөр бүр: prev_balance - debit + credit = balance_after
  opening_closing_tie: required # мета-блокийн үлдэгдэлтэй тулгах
  row_count_source: metadata_optional   # "Гүйлгээний тоо" байвал тулгана

2.1 Registry-ийн ажиллагааны дүрэм

  • Сонголт: Шат 1-д бүх идэвхтэй descriptor-ийн fingerprint-ийг файлтай тулгаж оноо тооцно. Хамгийн өндөр оноотой нь min_score-оос давбал сонгогдоно; хоёр descriptor ойролцоо оноотой бол хоёуланг нь ажиллуулж validation gate давсныг нь авна.
  • Таарахгүй бол: алдаа биш — Шат 1-ийн AI ангилагч (Fable 5) файлын эхний 100 мөрийг хараад хамгийн ойр descriptor-ийг санал болгох эсвэл «шинэ формат» гэж тэмдэглэнэ. Шинэ формат админ самбарт очиж, тэндээс шинэ descriptor-ийг AI-аар үүсгүүлж (жишээ файлаас draft descriptor гаргах), хүн баталгаажуулж registry-д нэмнэ.
  • Хувилбарын амьдралын мөчлөг: descriptor бүр active / deprecated / draft статустай; банк формат солиход хуучныг deprecated болгож шинийг нэмнэ — хуучин хуулга дахин боловсруулагдах үед хуучин descriptor хэвээр ажиллана.
  • Хэмжилт: descriptor бүрээр амжилтын хувь (validation gate давсан хувь) хянагдана; 98%-иас буусан descriptor админд анхааруулга өгнө (банк формат өөрчилсний дохио).

03Каноник гүйлгээний схем

Ямар ч банкны, ямар ч форматын хуулга задлагдсаны дараа ганц ижил хэлбэрт орно. Pipeline-ийн Шат 3-аас хойшхи бүх код зөвхөн энэ схемтэй ажиллана:

bank_txn {
  id                  uuid          -- системийн дотоод ID
  statement_id        uuid          -- аль хуулгаас гарсан
  company_id          uuid          -- tenant
  bank_account_id     uuid          -- дотоод дансны бүртгэлтэй холбоос
  seq_no              int           -- хуулга доторх дараалал (1-ээс)
  posted_at           timestamptz   -- ISO 8601, UTC+8
  direction           enum(debit, credit)
  amount_minor        bigint        -- мөнгө 100 (₮ → мөнгө); хэзээ ч float биш
  currency            char(3)       -- Үе 1: MNT
  balance_after_minor bigint | null -- гүйлгээний дараах үлдэгдэл (байвал)
  counterparty_account text | null  -- цэвэрлэгдсэн (зөвхөн цифр)
  counterparty_name    text | null  -- утгаас ялгасан бол
  description_raw     text          -- эх утга, өөрчлөхгүй
  description_norm    text          -- цэвэрлэсэн (олон зай, том/жижиг, орос-монгол хольц)
  channel_ref         text | null   -- банкны гүйлгээний дугаар (байвал)
  canonical_hash      char(64)      -- SHA-256, доорх томъёогоор
  extraction_path     enum(excel, pdf_text, vision)
  extraction_confidence numeric     -- vision зам: 2 уншилтын тохирц; бусад: 1.0
}

canonical_hash = SHA256(
  bank_account_id ‖ posted_at(минут хүртэл) ‖ direction ‖
  amount_minor ‖ counterparty_account ‖ normalize(description_raw)
)
Давхардлын хамгаалалт — 3 давхарга

(1) Файлын түвшин: SHA-256 ижил файл дахин орохыг хаана. (2) Гүйлгээний түвшин: canonical_hash дээр unique constraint — сар дамнуулан давхацсан хуулга (жишээ нь 1-6 сар, дараа нь 4-7 сар) оруулахад зөвхөн шинэ гүйлгээ нэмэгдэнэ. (3) Ижил хугацаанд, ижил дүнтэй, ижил утгатай жинхэнэ хоёр гүйлгээ байж болох тул hash-д seq_no-ийн оронд мөрийн дараалсан давталтын индексийг нэмнэ (ижил hash 2 дахь удаа гарвал suffix ‖2).

04Pipeline-ийн инженерийн тодорхойлолт

4.1 Шат 0-1 — Хүлээн авалт, таних

  • Upload үйлчилгээ: xlsx/xls/csv/pdf, ≤ 30MB; virus scan; объект санд company_id/statement_id/original.ext замаар хадгална; файлын SHA-256-аар давхардлыг татгалзана.
  • Файлын төрлийг өргөтгөлөөр биш magic bytes-аар тогтооно (xlsx=zip, xls=OLE2, pdf=%PDF).
  • Registry fingerprinting (§2.1). Үр дүн: statement.descriptor_id эсвэл needs_ai_routing.
  • Боловсруулалт async ажилладаг (queue); нябод progress харагдана. 10,000 мөртэй Excel ≤ 30 сек, 100 хуудастай PDF ≤ 5 мин зорилт.

4.3 Шат 3 — Нормчлол

  • Огноо: descriptor format → амжилтгүй бол хуулгын хугацааны мужид багтах ганц утга өгдөг format-ыг таамаглана; хоёрдмол байвал (01.02 vs 02.01) validation gate шийднэ — буруу таамаглал үлдэгдлийн гинжийг заавал тасалдаг.
  • Дүн: текст → minor unit бүхэл тоо. Мянгат/бутархайн тэмдэгт descriptor-оос; хаалт/хасах = сөрөг; хоосон = 0 биш NULL.
  • Чиглэл: separate горимд дебит ба кредит хоёулаа утгатай мөр алдаа; signed горимд тэмдэгээр тогтооно.
  • Утга: description_raw хэвээр; description_norm = olon зай нэгтгэх, IBAN/данс, ebarimt дугаар, огноог pattern-аар ялгаж counterparty_account, channel_ref талбарт салгана.

4.4 Шат 4 — Validation Gate (хатуу хаалт)

ШАЛГАЛТ V1 — Үлдэгдлийн гинж (balance_after байгаа үед, мөр бүрд):
    balance_after[i] == balance_after[i-1] - debit[i] + credit[i]
    balance_after[0] == opening_balance - debit[0] + credit[0]

ШАЛГАЛТ V2 — Нийлбэрийн тулгалт (үргэлж):
    opening_balance + Σcredit - Σdebit == closing_balance

ШАЛГАЛТ V3 — Мөрийн тоо: metadata-д заасан бол таарах ёстой
ШАЛГАЛТ V4 — Огноо: бүх мөр хуулгын мужид, үл буурах дарааллаар
ШАЛГАЛТ V5 — Залгамж: өмнөх хуулгын closing == энэ хуулгын opening
             (ижил дансны өмнөх statement байвал; зөрвөл "цоорхой" анхааруулга)
ШАЛГАЛТ V6 — Давхардал: canonical_hash unique
  • V1 тасарсан цэг = алдаатай мөрийн байршил. UI дээр тухайн мөрийг эх файлын (PDF бол хуудасны зургийн) хажууд харуулж, нябо гараар засна эсвэл Зам В-ээр дахин уншуулна. Бүх хуулгыг дахин оруулах шаардлага хэзээ ч гарахгүй.
  • balance_after байхгүй форматад V1 боломжгүй тул V2 + V5 хатуу, мөн тухайн descriptor reduced_assurance: true гэж тэмдэглэгдэж vision double-pass заавал ажиллана.
  • Gate давсан хуулга parsed_verified статустай болж л дараагийн шатанд орно. Энэ шалгалтууд нь LLM биш, цэвэр детерминистик код — тестээр 100% хамрагдана.

4.5 Шат 5-6 — AI ангилалт ба Review (Үе 1-ийн хүрээ)

Үе 1-д ангилалтын бүрэн pipeline-ийн суурь хувилбар орно: дүрэм давхарга (нябо-гийн regex/keyword дүрэм) → Fable 5 batch ангилалт (§6) → итгэлцлийн 3 сагс → Review UI (бөөнөөр батлах, засах, дүрэм болгон хадгалах). Компанийн санах ойн RAG нь Үе 2-т, гэхдээ өгөгдлийн бүтэц нь (батлагдсан ангилалт бүр хадгалагдах) Үе 1-ээс бэлэн байна.

  • Сангийн яамны ЖДБ-ийн стандарт дансны төлөвлөгөөг seed болгож суулгана (Мөнгө 10-11, Авлага 12, Бараа материал 21, ДҮ 214x, ҮХ 25, Өр төлбөр 31-33, Өмч 41, Орлого 51, ББӨ 61, Зардал 71 гэх бүтэцтэй, 4-8 оронтой шатлал).
